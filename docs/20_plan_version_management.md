# 方案版本管理与产品化前端优化

## 建设目标

TripSage Agent 的前端不再只展示“最新一次回答”，而是把每次智能体生成的旅行方案保存为一个版本。用户可以在初版、二次优化版和后续方案之间切换，对比工具调用、引用来源和行程差异，再基于任一版本继续编辑。

## 功能边界

当前版本管理采用“前端即时展示 + 后端 SQLite 持久化”的方案：

- 每次 `/api/chat/stream` 返回最终 `ChatResponse` 后，前端生成一个 `PlanVersion`。
- 首次生成标记为“初版”。
- 用户编辑行程后触发“二次优化”，新结果标记为“优化版 N”。
- 切换版本时，右侧工具洞察、决策模块、可编辑行程和聊天最新结果同步切换。
- 可编辑行程组件会跟随当前版本重置草稿，避免用户在不同版本之间混淆。
- 前端会把版本保存到后端 `plan_versions` 表，刷新页面后可按会话恢复。
- 两个版本之间可生成结构化差异，展示来源、工具、风险、天数和决策模块变化。

后续如果需要多用户长期协作，可以继续增加用户表关联和云端分享权限。

## 数据结构

前端新增类型：

```ts
export interface PlanVersion {
  id: string;
  name: string;
  createdAt: string;
  reason: string;
  response: ChatResponse;
}
```

字段说明：

| 字段 | 说明 |
| --- | --- |
| `id` | 前端生成的版本唯一标识 |
| `name` | 展示名称，如“初版”“优化版 1” |
| `createdAt` | 生成时间 |
| `reason` | 版本来源，如首次生成或基于编辑草稿二次优化 |
| `response` | 后端完整智能体结果，包含答案、行程、工具调用、来源和决策模块 |

## 数据库表

后端新增 SQLite 表：

```text
plan_versions
```

| 字段 | 说明 |
| --- | --- |
| `id` | 前端生成的版本 ID，主键 |
| `conversation_id` | 会话 ID，用于恢复同一次规划工作台 |
| `name` | 版本名称 |
| `reason` | 版本来源说明 |
| `response_json` | 完整 `ChatResponse` JSON |
| `created_at` | 版本创建时间 |

## 后端接口

| 接口 | 作用 |
| --- | --- |
| `POST /api/plan-versions` | 保存或覆盖当前方案版本 |
| `GET /api/plan-versions?conversation_id=...` | 按会话读取全部版本 |
| `GET /api/plan-versions/compare?base_id=...&target_id=...` | 比较两个版本 |

版本对比不额外调用大模型，使用结构化字段直接计算，保证响应速度和稳定性。

## 前端交互

新增“方案版本”轨道：

- 用横向时间线展示版本。
- 当前版本有明显高亮和“当前”标签。
- 每个版本展示生成时间、工具调用数和引用来源数。
- 点击版本后，主工作台内容立即切换。
- 当存在两个以上版本时，自动显示“版本差异”面板。

这让应用更像旅行决策工作台，而不是普通聊天机器人。用户可以保留探索过程，不会因为一次二次优化覆盖掉初版。

## 视觉优化策略

本轮前端按“中式旅行调度台”方向继续优化：

- 保持纸感、玉石绿、铁路蓝和朱砂红的多色系统，避免单一色系。
- 使用玻璃化顶栏、细密网格、轨道式版本卡片和克制阴影，强化专业感。
- 为决策卡片、版本卡片、可编辑行程加入轻量 hover 反馈，提升可操作性。
- 移动端保留横向版本轨道，避免卡片挤压导致信息不可读。
- 左右辅助栏在桌面端保持固定，便于持续查看条件、工具和来源。
- 版本差异面板采用指标矩阵，避免用户阅读长文本才能理解变化。

## 验收标准

- 用户发起一次规划后，出现“初版”。
- 用户编辑行程并点击“二次优化”后，出现“优化版 1”。
- 点击任意版本，页面的行程、决策模块、工具洞察和来源同步切换。
- 刷新页面后，当前会话版本可以从数据库恢复。
- 选择优化版时，可以看到相对初版的结构化对比。
- 前端 `npm run build` 通过。
- 后端 `ruff check app tests` 和 `pytest` 通过。
- 代码保留中文注释，关键状态变化可读、可维护。
