# 攻略输出产品化讨论记录

## 问题 1
### 遇到的问题（描述）
当前杭州攻略虽然已经具备按天拆分、地点卡、地图联动、预算与风险模块，但从真实用户阅读体验来看，仍然显得粗糙，主要体现在：

1. 叙事感太弱。用户问“杭州旅游攻略”，期待看到的是“为什么这么安排、先玩哪、哪里吃、整体气质是什么、适不适合自己”，而不是直接看到结构字段的平铺。
2. 重复较多但有效信息密度不高。`Day 卡片`、`地点清单`、`地点简介` 在重复同一批点位，页面很长，但读完之后用户仍然不够清楚这座城市的路线逻辑、体验节奏和玩法重点。
3. 存在明显的系统占位语。例如“来自详细攻略正文”“适合作为这一天的主线节点继续展开”等表达，不应该直接暴露给终端用户。
4. 当前输出更偏机器可计算，不偏用户可阅读。现有结构对地图、铁路、天气、二次编辑比较友好，但用户第一眼看到时，缺少“我真的想照这个去玩”的成品感。

### 讨论出的解决方案和原理
这类问题不能只靠修改一个 prompt 解决，因为当前项目已经形成了多模块联动：

1. 地图工作台依赖 `route_nodes`
2. 铁路工作台依赖出发地、目的地、日期、交通建议
3. 天气模块依赖 `weather_backup`
4. 可编辑行程依赖 `itinerary / structured_plan`
5. 前端详情页依赖 `travel_plan_view`

如果只是把模型正文写得更花、更长、更像旅游博文，反而容易造成：

1. 地图节点漂移
2. 铁路和天气建议与正文脱节
3. 可编辑行程与展示页语义不一致
4. 前后端重新从长文本里“猜”结构

因此，本轮讨论明确提出：把“机器执行层”和“用户阅读层”彻底分离。

原理：
工具链优先吃稳定结构，前端主页面优先消费成品展示层，聊天区优先消费自然叙事层，三层职责必须拆开。

## 问题 2
### 遇到的问题（描述）
当前输出虽然已经有 `structured_plan`、`travel_plan_view` 和自然语言回答，但三者之间的职责边界还不够清晰，导致：

1. 有些内容明明该由展示层负责，却仍在结构层或兜底正文里拼装
2. 有些结构字段本来只是给地图和铁路用，却被直接暴露给用户
3. 一旦想增强文案高级感，就容易牵连地图、铁路、天气和二次编辑

### 讨论出的解决方案和原理
正式把输出定义为三层协议：

1. `tool_plan`
   - 给工具和工作台使用
   - 强调地点顺序、交通段、预算、雨天备选、风险点
   - 这一层继续由 `structured_plan` 及相关结构承担
2. `render_plan`
   - 给前端攻略详情页使用
   - 强调用户阅读体验、模块编排、表达完整度
   - 这一层不直接承担地图精度要求，而是承担“像成品攻略”的要求
3. `narrative`
   - 给聊天区正文使用
   - 强调像一个成熟攻略作者在解释“为什么这样玩”

原理：
工具只吃结构，页面吃成品模块，聊天区吃叙事文本，避免任何一层同时承担全部职责。

## 问题 3
### 遇到的问题（描述）
如果后续继续只优化 `travel_plan_view` 的字段展示，而不新增真正的产品级展示协议，那么前端再怎么美化，也仍然是在“排字段”，而不是在“展示攻略”。

### 讨论出的解决方案和原理
建议新增一层专门面向用户阅读的 `render_plan schema`，至少包含以下维度：

1. `city_positioning`
2. `overview_reason`
3. `day_positioning`
4. `route_reason`
5. `morning_block / noon_block / afternoon_block / evening_block`
6. `food_story`
7. `photo_tip`
8. `reservation_tip`
9. `avoidance_tip`
10. `fallback_plan`

原理：
地图、铁路、天气继续只消费底层结构；前端主页面开始消费一份更像旅游攻略的展示层数据，这样才能从“工具台”升级为“成品页”。

## 问题 4
### 遇到的问题（描述）
当前前端详情页里，`地点清单` 和 `地点简介` 仍占据较大篇幅。它们对地图和结构联动有意义，但不适合作为主舞台内容。

### 讨论出的解决方案和原理
后续前端阅读顺序应调整为：

1. 先给“这次杭州怎么玩”的一句判断
2. 再给按天的路线理由和节奏安排
3. 再给美食、交通、预算、强度、风险与雨天替换
4. 最后再把地点清单、地点简介、地图节点作为辅助层展开

并同步执行两条规则：

1. `地点清单` 和 `地点简介` 降级为辅助模块，不再作为主内容长展开
2. “来自详细攻略正文”这类系统占位语全部隐藏

原理：
用户要先看到“像攻略”的结果，再去操作地图、铁路和二次优化，而不是先看到结构节点。

## 问题 5
### 遇到的问题（描述）
从大模型能力本身来看，用户问“杭州旅游攻略”时，真正想得到的不是地点列表，而是一种带判断力的路线建议。如果回答里只有按点拆解，而没有“为什么这么玩”，用户会天然觉得粗糙。

### 讨论出的解决方案和原理
理想回答方式应当是：

1. 先说这座城市适合怎么游
2. 再说为什么 2 天应该以西湖主线、灵隐寺、河坊街、夜景为核心
3. 每一天都给出：
   - 路线逻辑
   - 时间安排
   - 吃什么
   - 怎么移动
   - 预算和体力强度
   - 下雨时怎么替换
4. 最后再进入地图、铁路、预算、风险等可执行层

原理：
用户买单的是“这趟行程被理解并被讲明白”，不是“系统成功列出了节点”。

---

## 本轮结论
### 遇到的问题（描述）
当前项目已经具备较强的结构化规划能力和工具联动能力，但攻略成品层仍不够成熟，核心矛盾是：

1. 结构层已经能服务地图和工具
2. 展示层还不足以支撑“产品级攻略阅读体验”
3. 如果直接改 prompt，很容易牵动地图、铁路、天气、编辑链路

### 讨论出的解决方案和原理
本轮达成的最终结论是：

1. 不要只改 prompt
2. 不要让长文本继续承担地图和工具链的结构来源
3. 保留现有结构化内核，但新增专门的产品级展示层
4. 把当前前端从字段展示页升级为真正的攻略成品页

后续开发应优先推进：

1. 明确 `tool_plan / render_plan / narrative` 三层协议
2. 让前端优先消费 `render_plan`
3. 让地图、铁路、天气继续只消费底层结构化真相层

这意味着接下来的升级重点，不是“再润色几句文案”，而是一次结果协议、渲染协议与产品表达层的协同升级。
